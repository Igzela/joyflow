# 指标与验证计划

JoyFlow 先验证游客价值，再验证园区价值。所有数字都来自模拟、可用性测试或后续试点，不把预测写成已经发生的事实。

## 游客价值指标

| 指标 | 说明 |
|---|---|
| 必玩完成率 | 用户定义的核心项目中，最终完成的比例 |
| 等待时间 | 单项目及全天累计等待时间 |
| 无效步行 | 因折返、失效路线产生的额外步行 |
| 方案接受率 | 用户接受系统调整建议的比例 |
| 提醒误触发率 | 用户认为没有必要或不准确的主动提醒比例 |
| 收藏分享率 | 收藏卡被保存、浏览或分享的比例 |
| 满意度与复游意愿 | 游后问卷中的整体体验和再次到访倾向 |

## 园区价值指标

| 指标 | 说明 |
|---|---|
| 跨业态触达与转化 | 餐饮、演艺、零售或酒店服务是否在合适节点被接受 |
| 低峰资源利用 | 是否把部分游客引导至体验合适但拥挤度较低的资源 |
| 因排队放弃率 | 用户因等待过长而放弃必玩项目的比例 |
| 复游线索留存 | 未完成愿望、下次计划或会员触点是否被保留 |

## 验证顺序

1. **场景模拟**：使用8个项目和三类事件，验证硬约束、候选路线和状态回写。
2. **小规模可用性测试**：观察用户是否理解调整原因，是否觉得提醒频繁或冒犯。
3. **单园区接口 PoC**：对接脱敏或模拟的票务、核销、排队和场次接口。
4. **A/B 试点**：在相似日期和客流条件下，对比 JoyFlow 与常规游园方式。

## MVP 验收条件

- 每次重排都能指出明确触发事件；
- 所有候选都满足开放时间、场次、身高、预约和闭园等硬约束；
- LLM 的解释与确定性排序结果一致；
- 用户拒绝调整后，系统能够保留原计划或重新生成其他候选；
- 体验负荷提醒可以关闭，并且不使用摄像头或情绪识别；
- 收藏卡只能由已完成的真实或模拟核销事件生成；
- 缺少关键数据时，系统明确降级，而不是编造结果。
