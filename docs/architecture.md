# 系统架构与决策边界

## 1. 输入层

JoyFlow 的 MVP 接收以下模拟或用户输入：

- 项目核销与已完成项目
- 当前排队时间与项目开放状态
- 天气预报与降雨事件
- 演出场次与固定时间窗
- 餐厅容量或建议休息节点
- 家庭结构、必玩项目、目标模式、预算与剩余时间
- 用户主动反馈与方案接受/拒绝记录

## 2. 游客动态状态模型

状态模型只保存完成编排所需的有限字段：

```text
家庭结构
目标模式与必玩优先级
当前位置
已完成项目
剩余时间与预算
连续游玩时长
累计步行与休息情况
体验负荷估计
最近的主动反馈
```

“数字分身”是产品表达，技术上是一个有限、可解释、经用户授权更新的状态对象，不是监控式全量画像。

## 3. 决策链路

```text
数据事件
  → 更新游客状态
  → 判断是否超过触发阈值
  → 过滤硬约束
  → 生成多个可行候选路线
  → 确定性评分排序
  → LLM解释调整原因
  → 用户接受、拒绝或微调
  → 回写新计划和状态
```

## 4. 路线评分

先过滤不可行方案，再对可行候选进行加权评分：

```text
Score =
  必玩完成收益
  + 兴趣、天气与场次适配
  - 等待时间惩罚
  - 步行与折返惩罚
  - 体验负荷惩罚
  - 错过时间窗风险
```

硬约束包括项目开放时间、演出场次、身高或年龄要求、已预约时间、移动时间和闭园时间。商业收益不能压过游客体验；只有当两个方案体验价值接近时，才可作为次级排序因素。

## 5. LLM 的职责

LLM 可以：

- 把自然语言需求解析为结构化偏好
- 用自然语言解释候选方案和调整原因
- 处理用户追问与陪伴式互动
- 基于已经完成的体验生成故事卡文案

LLM 不可以：

- 直接计算或随意输出路线
- 绕过硬约束
- 把体验负荷推断说成确定事实
- 在没有数据时编造排队、预约或容量状态

## 6. 体验负荷

体验负荷根据年龄段、活动水平、连续游玩时长、项目强度、步行与休息形成低置信度指标。超过阈值时，系统先询问用户是否调整，并提供“接受调整、继续原计划、只减少步行、暂不提醒”等选择。
