# MVP 演示场景

## 目标家庭

- 两名成人和一名儿童
- 目标模式：必玩优先
- Top 3：熊猫互动、过山车、15:30演出
- 可接受中等步行，希望下午安排一次休息

## 初始计划

系统根据开放时间、演出场次、预计排队、移动时间和家庭目标生成初始路线，并在14:00附近保留休息缓冲。

## 事件一：排队暴增

11:20，过山车排队从30分钟升至90分钟。

系统完成以下动作：

1. 标记原计划需要重排；
2. 生成多个满足演出时间窗的候选方案；
3. 按必玩完成、等待、步行和体验节奏排序；
4. 推荐先去熊猫互动，傍晚返回过山车；
5. 用自然语言说明预计节省的等待时间，并请求确认。

示例解释：

> 过山车当前排队约90分钟。先去熊猫互动，再于傍晚返回，预计少等45分钟，也不会错过15:30的演出。是否调整？

## 事件二：降雨预警

14:00，天气事件显示45分钟后降雨。

系统把雨中的户外项目移至雨后，并在不影响固定演出的前提下插入室内演出、餐饮或休息节点。用户接受后，新的路线和剩余时间写回状态模型。

## 事件三：体验负荷升高

15:40，家庭连续活动时间与累计步行超过保守阈值。

系统不直接判断“孩子累了”，而是提示：

> 已经连续活动较长时间，接下来两个项目还需要步行。要不要先休息20分钟？调整后仍能完成今天的必玩项目。

用户可接受、拒绝或只要求减少步行。

## 高价值体验与收藏卡

熊猫互动或演出核销完成后，系统生成对应的虚拟体验收藏卡。卡片只基于真实完成事件，可包含时间、地点、家庭成员与一句个性化故事。完成主题任务后可获得数字纪念内容或适度权益，但不得为了集卡或消费把用户导向低质量路线。

## 游后结果

演示结束时展示：

- 已完成和未完成项目
- 预计节省的等待与步行
- 用户接受和拒绝过的调整
- 已获得的体验收藏卡
- 未完成愿望与下一次复游建议

Demo 的核心不是展示大量功能，而是让评委看清每次变化由什么事件触发、系统为什么调整、用户是否接受，以及新状态如何回写。
